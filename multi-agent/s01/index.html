워크플로와 에이전트는 다르다

워크플로 (workflow)
코드가 순서를 정한다
LLM과 도구를 미리 정한 코드 경로로 엮는다. 예측 가능하고 싸다.
에이전트 (agent)
모델이 순서를 정한다
LLM이 스스로 과정과 도구 사용을 결정한다. 유연하지만 비싸고 예측이 어렵다.

에이전트 하나로는 왜 부족해지나

컨텍스트 포화
읽은 자료, 도구 결과, 시행착오가 한 창에 쌓인다. 길어질수록 앞의 지시를 놓치고, 결국 창이 넘친다.
예: 논문 40편 초록을 한 대화에서 비교
순차 실행
한 번에 한 가지씩. 서로 독립적인 조사 10건도 줄을 서서 기다린다.
예: 데이터셋 10개 라이선스 확인
역할 혼재
같은 창에서 쓰고, 검토하고, 채점한다. 자기 결과물에는 후해지기 쉽다.
예: 자기가 짠 실험 코드를 자기가 리뷰

② 대표 패턴

LLM을 엮는 다섯 가지 기본 패턴

1 · Prompt chaining
체인
앞 단계 출력이 다음 단계 입력. 사이에 코드 검사를 끼울 수 있다.
초록 요약 → 한국어 번역 → 용어 통일
2 · Routing
라우팅
입력을 분류해 전문 처리기로 보낸다.
문의 → 장비 / 행정 / 연구 담당
3 · Parallelization
병렬화
독립 부분을 동시에(분할) 또는 같은 일을 여러 번(투표).
한 코드를 보안·성능·가독성 관점에서 동시 검토
4 · Orchestrator–workers
오케스트레이터–워커
중심 LLM이 실행 중에 일을 쪼개 맡기고 결과를 합친다.
연구 질문 → 하위 질문 n개 → 종합
5 · Evaluator–optimizer
작성–검토 루프
하나가 만들고 하나가 평가·피드백, 기준을 넘을 때까지 반복.
논문 초안 ↔ 심사위원 역할
+ Autonomous agent

사례: 중앙형 리서치 시스템

구조

대가

왜 잘됐나

브라우징 평가에서 성능 차이의 약 80%가 쓴 토큰 양으로 설명됐다.

멀티 에이전트는 창을 여러 개 써서 한 창으로는 못 쓰는 양의 토큰을 문제에 쏟게 해 준다. 그래서 폭넓게 병렬로 찾는 일에 강하다.

7개 프레임워크의 실행 기록 1,600여 건을 분석해 14가지 실패 유형을 3갈래로 묶은 연구 (MAST)

명세 · 설계 문제

대화가 처음으로 되돌아감, 모르면서 묻지 않음, 정보를 넘기지 않음, 남의 의견 무시, 말과 행동이 다름

실습 준비

첫 호출과 토큰 확인

import anthropic
client = anthropic.Anthropic()          # 환경 변수에서 키를 읽음
MODEL = 'claude-sonnet-5-5'

resp = client.messages.create(
    model=MODEL, max_tokens=500,
    system='너는 간결한 연구 조교다.',
    messages=[{'role': 'user', 'content': '멀티 에이전트를 한 문장으로 정의해 줘.'}],
)
print(resp.content[0].text)
print(resp.usage.input_tokens, resp.usage.output_tokens)
여러 LLM 에이전트가 역할을 나눠 협력하며 하나의 목표를 이루는 시스템입니다.
31 38
  • system: 이 에이전트의 지침
  • messages: 대화 기록 = 컨텍스트
  • usage: 비용 계산의 근거 — 매번 기록한다
