친구 A의 AI

제출해 보니 코드는 실행도 안 되고, 원본 데이터 파일은 지워져 있다. 다음 날 물어보면 어제 한 일을 전혀 기억하지 못한다.

친구 B의 AI

"테스트 12개 모두 통과했습니다"

규칙대로 작성했고, 스스로 실행해 검증했고, 위험한 명령은 막혔다. 어디까지 했는지 기록도 남겨 두었다.

힌트: 두 사람은 같은 모델을 쓰고 있습니다. 다른 건 모델 바깥입니다.

손들기 질문: "AI한테 과제 시켜 본 사람?" "AI가 다 했다고 했는데 실제로는 안 돼 있던 경험?" 2~3명 답을 듣는다. 정답을 말하지 말고 "오늘 이 차이의 정체를 알아봅니다"로 넘어간다.
단어부터

Harness = 말에 채우는 마구(馬具)

  • 말은 힘이 세고 빠르지만, 혼자서는 어디로 갈지 모릅니다.
  • 마구(고삐·안장·굴레)는 그 힘에 방향을 주고, 위험할 때 멈추게 합니다.
  • 좋은 마구가 있어야 말의 힘이 쓸모 있는 일이 됩니다.
🐎 말  →  AI 모델 (GPT, Claude, Gemini…)
🪢 마구  →  하네스 (도구·규칙·검사·기록)
🧑‍🌾 마부  →  하네스 엔지니어 = 여러분

※ 소프트웨어에서는 원래 '테스트 하네스'(테스트를 돌리는 틀)라는 말도 써 왔습니다. 오늘의 하네스는 그 개념을 AI 에이전트 전체로 넓힌 것입니다.

비유를 확실히 심어 두면 나머지가 쉬워진다. "말을 더 빠른 말로 바꾸는 것(모델 교체)보다, 마구를 잘 채우는 것이 실제 농사에는 더 중요할 때가 많다."
01

AI 에이전트란?

말(모델)은 혼자서 무엇을 할 수 있고, 무엇을 못 할까

01 · AI 에이전트란?
모델 혼자서는

언어 모델(LLM)은 '다음 글자 예측기'입니다

입력 (글)
"평균을 구하는 함수를…"
↓ LLM ↓
"def mean(xs): ..."
출력 (글)

글이 들어가면 글이 나온다. 그게 전부입니다.

그래서 혼자서는…

  • 손이 없다 — 파일을 열거나 코드를 실행할 수 없음
  • 눈이 없다 — 자기가 쓴 코드가 진짜 되는지 확인 불가
  • 기억이 없다 — 대화가 끝나면 다 잊음 (컨텍스트 창의 한계)
  • 브레이크가 없다 — 무엇이 위험한지 스스로 막지 못함
핵심: 모델은 매우 똑똑하지만 '몸'이 없다. 컨텍스트 창 = 한 번에 볼 수 있는 글의 양, 사람의 작업 기억 같은 것이라고 짧게 설명. 이 4가지 결핍이 뒤에서 하네스 부품 4~6개로 그대로 대응된다는 걸 기억해 두라고 예고.
01 · AI 에이전트란?
챗봇 vs 에이전트

말해 주는 AI → 해 주는 AI

챗봇
이 버그 어떻게 고쳐?
아마 7번째 줄이 문제 같아요. 이렇게 바꿔 보세요: …
(복사 → 붙여넣기 → 실행 → 에러 → 다시 질문…)

실행·확인은 사람이 한다

vs
에이전트
이 버그 고쳐 줘.
▶ grade.py 파일 읽기
▶ python grade.py 실행 → 오류 확인
▶ 코드 수정
▶ 테스트 실행 → 1개 실패 → 다시 수정
✓ 테스트 3/3 통과. 수정 내용 보고

실행·확인을 AI가 스스로 반복한다

Claude Code, OpenAI Codex, Cursor 같은 '코딩 에이전트'가 오른쪽의 대표 예. 오른쪽에서 AI가 파일을 읽고 실행할 수 있는 건 모델이 아니라 '하네스'가 그 능력을 줬기 때문이라는 점을 미리 짚는다.
01 · AI 에이전트란?
에이전트의 심장

에이전트 루프: 생각 → 행동 → 관찰 → 반복

모델이 하는 일은 ① 하나뿐.

②~④를 가능하게 하는 모든 것 — 도구를 연결하고, 결과를 다시 보여 주고, 언제 멈출지 정하는 것 — 이 바로 하네스입니다.

사람이 숙제할 때도 똑같죠: 계획 → 해 보기 → 채점해 보기 → 고치기.

주황 점이 돌아가는 걸 보여 주며 설명. "모델은 이 원의 1/4만 담당한다. 나머지 3/4는 사람이 설계한 코드와 환경이다." 이 슬라이드가 오늘 강의의 개념적 중심.
01 · AI 에이전트란?
오늘의 공식
에이전트 = 모델 + 하네스

하네스 = 에이전트에서 모델을 뺀 나머지 전부

모델

원재료가 되는 지능. 회사가 만들어 제공. 우리가 직접 바꾸기는 어렵다.

하네스

도구·규칙·검사·기록·권한. 우리가 설계하고 고칠 수 있는 부분.

예시

Claude Code, OpenAI Codex, Cursor는 모두 모델 위에 씌운 '기성품 하네스'.

출처: Birgitta Böckeler, "Harness engineering for coding agent users", martinfowler.com (2026.4)

이 공식은 업계에서 널리 쓰이는 표현. 강조점: 모델은 우리가 못 바꾸지만 하네스는 우리가 바꿀 수 있다 → 그래서 '엔지니어링'의 대상이 된다. 같은 모델이라도 하네스에 따라 성능이 크게 달라진다는 것이 1번 질문(친구 A/B)의 답.

03 · 실제 사례
용어의 탄생 · 2026년 2월

"같은 실수를 두 번 하지 않게 만든다"

Terraform을 만든 개발자 미첼 하시모토는 AI 활용기를 정리한 글에서, 에이전트가 실수할 때마다 그 실수가 다시는 일어나지 않도록 환경을 고치는 습관을 'Engineer the Harness'라고 불렀습니다.

방법은 두 가지:

  • 지침 보강 — AGENTS.md에 규칙 한 줄 추가
  • 도구 제작 — 스크린샷 스크립트, 필터링된 테스트 실행기 등

❌ 보통의 대응

"아니 그거 말고… 다시 해 줘" (매번 반복)

✅ 하네스 엔지니어의 대응

"왜 틀렸지? → 규칙·테스트를 추가해서 영원히 막자"

출처: Mitchell Hashimoto, "My AI Adoption Journey" (2026.2.5)

핵심 메시지: 하네스는 한 번에 완성하는 게 아니라 실패를 관찰하며 '누적'되는 것. 프롬프트를 다시 치는 건 일회성, 환경을 고치는 건 영구적. 이 차이가 엔지니어링.
03 · 실제 사례
OpenAI Codex 팀 · 2026년 2월

사람이 코드를 한 줄도 직접 쓰지 않은 제품

3명
에이전트를 운영한 엔지니어 (초기)
≈1,500
병합된 Pull Request 수
≈100만
줄의 코드 — 모두 에이전트가 작성

😮 처음엔 느렸다

에이전트가 무능해서가 아니라 환경이 덜 갖춰져서. 도구도, 구조도, 문서도 부족했다. 그래서 엔지니어의 일이 '코드 작성'에서 '에이전트가 일할 수 있게 만들기'로 바뀌었다.

🔧 그들이 만든 하네스

앱 화면·로그·지표를 에이전트가 직접 볼 수 있게 연결 → 버그 재현과 수정 검증을 스스로 수행. 설계 문서와 품질 점수표를 저장소에 두고, 에이전트끼리 서로 리뷰.

출처: Ryan Lopopolo, "Harness engineering: leveraging Codex in an agent-first world", OpenAI (2026.2.11)

세 문제로 정리해 봅시다

Q1. 다음 중 '하네스'에 해당하지 않는 것은?
하네스 = 에이전트에서 모델을 뺀 나머지. 가중치는 모델 그 자체입니다.
Q2. 에이전트가 일을 마친 후 오류를 찾아내 스스로 고치게 하는 장치는?
행동 후에 감지하는 것은 센서. 테스트·린터·AI 리뷰어가 대표적입니다.
Q3. 에이전트가 같은 실수를 반복합니다. 하네스 엔지니어다운 대응은?
실수를 환경 수준에서 영구히 막는 것 — 하시모토가 말한 'Engineer the Harness'.
학생들에게 손가락(1~4)으로 답하게 한 뒤 클릭해 정답 공개. 오답 선택지도 하나씩 왜 아닌지 짧게.
